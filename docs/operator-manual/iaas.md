# Compute: инстансы, группы размещения, диски, снимки и SSH-ключи

В меню «Все сервисы» откройте **Infrastructure → Compute**. Прежнее название
этого продукта — IaaS. Техническое имя `Product/iaas` и адреса страниц сохраняются.

Один `Product/iaas` объединяет инстансы, диски, снимки и SSH-ключи. Каждый тип задаётся
отдельным `ProductResource`, а его список, карточка и форма — несколькими
`ProductPage`. Одна сущность соответствует одному основному CR. Для VM, диска и ключа это штатный managed resource Crossplane;
для снимков используется отдельно устанавливаемый мини-оператор.

## Консоль виртуальной машины

В карточке ВМ выберите вкладку **Консоль**: VNC откроется автоматически внутри
страницы. **Переподключить** получает новую временную сессию, **Полный экран**
расширяет область консоли, если браузер поддерживает этот режим. Перейдя на другую
вкладку, вы закрываете встроенное соединение. Работа ВМ продолжается.

Это экран и клавиатура гостевой ОС. Для входа нужна учётная запись гостя;
импортированный SSH-ключ сам по себе не создаёт пароль для входа через VNC.
Если ВМ ещё создаётся или её консоль недоступна, проверьте состояние и повторите.

Подключение требует чтения InstanceV2 и отдельного Kubernetes RBAC verb `connect`
для `instancev2s.compute.openstack.m.crossplane.io` в проекте. Продуктовая роль
editor и наследующая её owner включают connect; viewer не получает интерактивный
доступ от одного права чтения. Сессия привязана к UID выбранной ВМ: после
пересоздания откройте новый ресурс из списка.

Для установки включите `iaas.console.enabled` в OpenStack integration chart,
задайте `existingSecret` с ключом `token` и `publicURLs` по именам подключений.
В Dashboard подключите одноимённый адаптер через `resourceSessions.adapters` с
тем же сервисным credential и разрешёнными HTTPS origins. Доступ к Secret
проектов остаётся только у интеграции, пользовательский токен ей не передаётся.
При необходимости `iaas.console.proxies` создаёт ingress-nginx TLS/WebSocket
прокси к внутреннему Nova noVNC: `address`, `host`, `clusterIssuer` и
необязательный `ingressClassName`. Для другого ingress настройте эквивалентный
прокси самостоятельно. Не журналируйте query parameters VNC URL: они содержат
временный токен. Вкладка описана обычной JSON Schema, см.
[встроенные сессии](resource-pages.md#встроенные-сессии).

На всех Nova compute задайте `[vnc] novncproxy_base_url` с тем же внешним HTTPS
URL до `vnc_lite.html` и примените конфигурацию штатным способом управления вашим
OpenStack. Nova проверяет схему Origin браузера по access URL токена: одной
замены адреса в адаптере недостаточно. Не отключайте Origin validation.

## Возможности

| Ресурс | Основной CR | Действия |
| --- | --- | --- |
| Инстанс | InstanceV2, compute.openstack.m.crossplane.io/v1alpha1 | Создание, просмотр, изменение имени/описания/меток, смена flavor после остановки, запуск, остановка, VNC-консоль, удаление |
| Диск | VolumeV3, blockstorage.openstack.m.crossplane.io/v1alpha1 | Создание, просмотр, имя/описание/метки, увеличение размера, снимок, удаление |
| Снимок диска | VolumeSnapshot, storage.gatorstack.dev/v1alpha1 | Создание из диска, просмотр, имя/описание/метки, создание нового диска, удаление |
| SSH-ключ | KeypairV2, compute.openstack.m.crossplane.io/v1alpha1 | Импорт публичного ключа, просмотр, удаление |
| Группа размещения | ServergroupV2, compute.openstack.m.crossplane.io/v1alpha1 | Создание с одной из четырёх стратегий, просмотр состава, удаление пустой группы |
| Подключение диска | VolumeAttachV2, compute.openstack.m.crossplane.io/v1alpha1 | Подключение к VM, состояние/устройство, отключение с сохранением VM и диска |

Образы, flavors и типы дисков выбираются из подключённого OpenStack. Смена региона
сбрасывает выбор зависимых полей. В форме инстанса выберите регион и зону,
затем flavor, образ, готовую подсеть [VPC](vpc.md) и ранее импортированный SSH-ключ
этого региона. Подсети доступны только из выбранного проекта, региона и зоны.
Приватный ключ не загружается в консоль. Для SSH-соединения с VM также нужны
разрешённая сеть, маршрутизация и правила безопасности вашего OpenStack.

Форма создания разделена на общую информацию, образ и загрузочный диск,
вычислительные ресурсы, сеть, доступ и дополнительные настройки. Размер
загрузочного диска задаётся в GiB; диск создаётся через blockDevice того же
InstanceV2 и удаляется вместе с VM. Cloud-init задаётся только при создании. По умолчанию форма и шаблон заказа содержат `ssh_pwauth: false`: используется выбранный SSH-ключ. Сохраните эту настройку в своём user-data, если парольный SSH не требуется.
В списке flavors показаны vCPU, RAM и размер локального диска конфигурации;
размер загрузочного volume задаётся отдельно.

Карточка содержит вкладки «Обзор», «Диски», «Сеть», «Доступ» и «Диагностика».
Пути и подписи задаёт JSON Schema ProductPage. ID, адрес и SSH-команду можно
скопировать. Команда в примере рассчитана на стандартный образ Ubuntu 24.04;
для другого образа оператор меняет её префикс в schema. Вкладка «Диски»
показывает загрузочный blockDevice основного CR и таблицу управляемых VolumeAttachV2.
Подключения, созданные вне этого контракта, могут отсутствовать в управляемой таблице;
фактические подключения диска дополнительно видны в наблюдениях Cinder.
У старых VM с локальным загрузочным диском этот массив может отсутствовать.

Для смены конфигурации остановите VM и дождитесь наблюдаемого состояния
shutoff и убедитесь, что нет нового запроса запуска. В форме изменения выберите
новый flavor того же облака. Пустой выбор
сохраняет прежний flavor. Проверка состояния выполняется сервером; подмена
облака в запросе запрещена. Изменение имени OpenStack не меняет имя или UID CR.
Образ, сеть, SSH-ключ и cloud-init не редактируются: их изменение может
пересоздать или перестроить VM. Сначала дождитесь готовности импортированного
SSH-ключа: только готовые и синхронизированные ключи доступны для нового заказа.

Операция создания записывает CR. Готовность внешнего объекта определяется
статусом провайдера. Состояние питания берётся из status.atProvider.powerState;
conditions Ready/Synced показываются отдельно. Созданный Kubernetes CR ещё не
подтверждает готовность VM или гостевой ОС. Удаление также может занимать время
до завершения finalizer провайдера.


## Группы размещения ВМ

Откройте **Compute → Группы размещения → Создать**. Укажите имя, необязательное
описание и метки, регион и стратегию. Дождитесь готовности и синхронизации группы.
В списке показаны имя, статус, стратегия, регион и дата создания. В карточке
доступны обзор, виртуальные машины и диагностика провайдера.

| Стратегия Nova | Размещение |
| --- | --- |
| `affinity` | Все ВМ на одном вычислительном хосте |
| `soft-affinity` | Предпочтительно на одном хосте; при нехватке ресурсов допускаются разные хосты |
| `anti-affinity` | ВМ на разных вычислительных хостах; нехватка подходящих хостов приводит к ошибке планирования |
| `soft-anti-affinity` | Предпочтительно на разных хостах; допускается совместное размещение |

При **создании инстанса** в секции **«Расположение»** выберите необязательную
**«Группу размещения»**. Предлагаются только готовые группы того же проекта и
региона. Смена региона очищает выбор. Группа относится к региону; зона ВМ
выбирается отдельно. Например, строгая affinity несовместима с размещением ВМ
одной группы в разных зонах, если зоны состоят из разных хостов.

Nova задаёт членство при создании ВМ. Изменить стратегию или имя существующей
группы, добавить уже работающую ВМ либо перенести её в другую группу через
консоль нельзя. Для другой стратегии создайте новую группу и новые ВМ.
На вкладке **«Виртуальные машины»** таблица показывает заявленные CR этого
проекта и региона, а поле состава Nova — наблюдаемые UUID внешних ВМ. Пока
провайдер создаёт ВМ, эти данные могут различаться. Удалять группу можно после
удаления её ВМ и подтверждения пустого состава провайдером.
Консоль также повторно проверяет связанные CR, включая создаваемые и удаляемые
ВМ: задержка обновления состава Nova не разрешает удаление занятой группы.
Для этой проверки нужны права чтения списка ВМ. Отказ RBAC блокирует удаление.

Для оператора: основной ресурс группы — штатный namespaced `ServergroupV2`.
`ProductResource/iaas-placement-groups` и три `ProductPage` входят в пакет Compute.
Роль `iaas.viewer` читает группы, `iaas.editor` создаёт и удаляет их. Описание
сохраняется в `metadata.annotations["compute.gatorstack.dev/description"]`,
метки — в `metadata.labels`; Nova не предоставляет полей описания и меток группы.
Метка `iaas.gatorstack.dev/cloud` задаётся подключением автоматически.

```yaml
apiVersion: compute.openstack.m.crossplane.io/v1alpha1
kind: ServergroupV2
metadata:
  name: application-spread
  namespace: my-project
  annotations:
    compute.gatorstack.dev/description: Разделить реплики приложения
  labels:
    iaas.gatorstack.dev/cloud: my-region
    application: backend
spec:
  providerConfigRef:
    kind: ProviderConfig
    name: my-region
  forProvider:
    name: application-spread
    policies:
      - anti-affinity
```

В namespace проекта должны существовать `ProviderConfig/my-region` и его
connection Secret. Lookup проверяет права пользователя, регион, UID, ревизию содержимого,
Ready/Synced и отсутствие удаления, затем записывает внешний UUID группы в
`InstanceV2.spec.forProvider.schedulerHints[0].group`. Начальная подготовка
сети повторно проверяет группу перед снятием паузы ВМ. После создания экземпляра
adapter сохраняет последующие административные паузы.
Изменение состава `members` и служебного `resourceVersion` не сбрасывает выбор;
смена UUID, политики либо готовности требует обновить выбранную группу.

Для soft-стратегий Nova должна поддерживать microversion 2.15 и соответствующие
scheduler weighers; для строгих стратегий нужны filters affinity/anti-affinity.
Проверьте также квоты Nova на число групп и участников. Разделение хостов
не гарантирует отдельные стойки или площадки и само по себе не обеспечивает HA.
Семантика и неизменяемость описаны в [руководстве Nova](https://docs.openstack.org/nova/2024.2/user/server-groups.html).
Условия удаления в Dashboard не ограничивают прямой доступ к Kubernetes API;
его права и admission настраивает оператор.

## Региональные каталоги образов

Образ загружается в Glance выбранного облака. Синхронизация публикует доступные
tenant-подключению активные образы как штатные Observe-only
`ImageV2.images.openstack.m.crossplane.io/v1alpha1` в namespace каталога.
В JSON Schema источник и региональный фильтр уже описаны GVK lookup: новые ОС
появляются без изменения кода Dashboard. Образы другого региона не предлагаются.
Импорт в один Keystone не переносит содержимое в другой — загрузите отдельную
копию, если образ нужен в нескольких регионах.

Используйте официальные cloud images amd64/x86_64 с cloud-init, проверьте
контрольную сумму поставщика и виртуальный размер qcow2. Для FreeBSD выбирайте
BASIC-CLOUDINIT, например UFS, а не обычный VM image без инициализации облака. Он использует штатный nuageinit; поддерживаемые параметры user-data описаны в [nuageinit(7)](https://man.freebsd.org/cgi/man.cgi?query=nuageinit&sektion=7). Для Cinder/KVM задайте image properties `hw_disk_bus=scsi`, `hw_scsi_model=virtio-scsi` и `img_config_drive=mandatory`. Config drive передаёт metadata и ключи без [зависания DHCP в исходном nuageinit образа 15.1](https://cgit.freebsd.org/src/commit/libexec?id=13d5f20e5b9ecb42ecf7de4e98d5af0bd5d63c82).
Сжатый qcow2.xz сначала распакуйте. Нельзя загружать образ, зависящий от внешнего
backing file. Размер загрузочного диска должен быть не меньше virtual size и
Glance min_disk; min_ram должен соответствовать выбранному flavor.
CentOS Stream 10 требует CPU с x86-64-v3, включая виртуальный CPU гостя.

Пример импорта подготовленного и проверенного файла:

```sh
openstack --os-cloud my-region image create debian-13-amd64 \
  --disk-format qcow2 --container-format bare --file debian-13-amd64.qcow2 \
  --public --min-disk 3 --min-ram 1024 \
  --property architecture=x86_64 --property os_distro=debian \
  --property os_version=13 --property os_admin_user=debian \
  --property gator_title=Debian --property gator_group=Debian \
  --property 'gator_variant=13 · x86_64' \
  --property 'gator_description=Debian 13 Trixie с cloud-init. Пользователь SSH: debian.'
```

Для `--public` нужны соответствующие права OpenStack. Вместо публикации для всех
проектов можно настроить image sharing и membership целевого tenant. Видимость
проверяется OpenStack, а доступ к ImageV2 — Kubernetes RBAC.
`gator_icon` принимает разрешённый image URL или base64 data URI; при его отсутствии
используется нейтральный значок. Значения `gator_title/group/variant/description/icon`
синхронизируются в аннотации `catalog.gatorstack.dev/title`, `group`, `variant`,
`description`, `icon`. `iaas.imageCatalog` в Helm values может переопределять их
по UUID или имени, не меняя содержимого образа.

Стандартные пользователи официальных образов:

| Образ | Пользователь SSH |
| --- | --- |
| Ubuntu 22.04 / 24.04 LTS | ubuntu |
| Debian 13 | debian |
| CentOS Stream 10 | cloud-user |
| FreeBSD 15.1 BASIC-CLOUDINIT | freebsd |

Доступ выполняется по выбранному SSH-ключу. Проверяйте имя пользователя в
описании образа; команда из карточки ресурса может содержать префикс,
настроенный оператором в JSON Schema. После импорта дождитесь успешной
синхронизации каталога, проверьте регион, карточку и тестовую загрузку с SSH.
Не заменяйте содержимое уже используемого образа под прежним UUID: новый build
публикуйте отдельным образом, сохраняя старые VM и их источник.

## Подключить и отключить диск

В карточке VM нажмите **«Подключить диск»** и выберите свободный диск. В карточке
диска можно начать с **«Подключить к ВМ»**. Облако берётся из исходного ресурса;
форма показывает только ресурсы выбранного проекта, ProviderConfig и зоны.
Готовность, UID/resourceVersion и фактическое подключение проверяются повторно
на сервере. Передать UUID чужого диска или другой namespace вместо выбора нельзя.
Если выбранный вариант обновился, повторите выбор по свежим данным каталога.

Форма подключения открывается поверх карточки. После выбора диска нажмите
**Подключить**: консоль вернёт вас на исходную вкладку с состоянием операции и
устройством. **Отменить** и крестик закрывают окно без изменений. Подтверждение
недоступно, пока обязательные поля не заполнены. Из карточки диска доступен такой
же сценарий с выбором ВМ.

Создаётся штатный Crossplane `VolumeAttachV2` в namespace проекта. Дождитесь
Ready/Synced и фактического имени устройства. Запрошенное имя `/dev/vdb` необязательно:
гипервизор может назначить другое. Создание CR ещё не означает появления диска
в гостевой ОС; создание файловой системы и монтирование выполняются отдельно.

На вкладке «Диски» VM и «Подключения» диска показана таблица подключений. Нажмите
**«Отключить диск»** прямо в нужной строке. Перед подтверждением размонтируйте файловые
системы в гостевой ОС. Удаляется только attachment CR; finalizer Crossplane ждёт
отключения в Nova/Cinder. VM и VolumeV3 сохраняются. Загрузочный blockDevice этим
сценарием не отключается. Multiattach и принудительное отключение не включены.

Один диск имеет один слот подключения по UID, включая конкурентные действия из
разных карточек. Новое подтверждение не создаёт второй CR, пока старое подключение
занимает слот. После завершения detach можно подтвердить новое подключение;
повтор старого запроса не создаёт результат заново и не затрагивает новый UID.
Имена/UID источников и cloud задаются mappings и relations в поставляемых манифестах.
[Контракт связанных таблиц](resource-pages.md#связанные-ресурсы) применяется к любому GVK.

Для чтения нужны get/list/watch VolumeAttachV2; для подключения — create, для
отключения — get/delete. IaaS viewer/editor/owner поставляемого пакета включают
соответствующие права. Скрытые страницы подключения не добавляют пункт меню.
Ограничения консоли не заменяют OpenStack tenant scope credentials и правила
admission/RBAC для пользователей с прямым доступом к Kubernetes API провайдера.

## Типы дисков и снимки

Тип диска выбирается из Crossplane VolumeTypeV3 подключённого облака. В схеме
нет enum названий типов. При смене облака выбор сбрасывается. Сервер проверяет
UID/version, публикацию, label облака и ProviderConfig выбранного типа. Каталоги
двух облаков могут иметь разные названия и количество предложений. Выбор типа
доступен для самостоятельного диска и загрузочного volume VM.

Типы Cinder создаёт администратор OpenStack и связывает с нужными backend/QoS.
HDD/SSD/NVME — названия предложений, сами по себе они не гарантируют физический
носитель или IOPS. Для лаборатории возможны три логических профиля на общем LVM;
для разных физических классов настройте соответствующие backend в Cinder.

В карточке диска нажмите «Создать снимок», задайте имя, описание и метки.
Раздел «Снимки дисков» показывает состояние, размер исходного диска, источник,
дату, ID, метки и облако. В карточке снимка доступны изменение имени/описания/меток,
удаление и «Создать диск». Новый диск создаётся из этого снимка в том же облаке;
размер не может быть меньше исходного. Исходный диск при восстановлении не
перезаписывается. Расписания и согласование с приложением внутри VM в этот
сценарий ручных снимков не входят.

Установленный пакет provider-openstack не содержит Snapshot MR. Снимки добавляет
отдельный компонент **gator-openstack-storage** со своим Helm chart и
`VolumeSnapshot.storage.gatorstack.dev/v1alpha1`. Это собственный CRD мини-оператора,
а не штатный GVK Crossplane. Без его установки формы снимков не подключают.
Оператор читает ProviderConfig и connection Secret namespace заказа; credentials
не попадают в браузер. Он управляет статусом/finalizer снимка, ищет результат
прерванного Cinder POST по UID CR и не отправляет POST повторно вслепую.
При CreationOutcomeUnknown проверьте внешний снимок и UID перед восстановлением;
finalizer сохраняется до подтверждения, чтобы не потерять внешний объект.

При удалении снимка finalizer ждёт удаления в Cinder. Снимки не удаляются
автоматически вместе с исходным диском. Если Cinder запрещает удаление используемого
снимка, причина отражается conditions; принудительное удаление не подставляется.

Отдельный addon каталога gator-openstack публикует наблюдаемые Cinder status, encryption, дату и подключения
диска в storage.gatorstack.dev annotations основного VolumeV3. Он не меняет его
spec/status Crossplane. Это позволяет строить колонки через обычные JSON paths.
Пустое значение означает отсутствие данных; неподтверждённый публичный IP не
подменяется внутренним адресом VM.

Остановка/запуск, расширение диска и создание связанных ресурсов используют
[общие действия](resource-actions.md). Applied подтверждает запись CR; готовности
внешнего объекта нужно дождаться отдельно.

### Установка мини-оператора снимков

Мини-оператор требует существующих namespaced ProviderConfig и connection Secrets
`openstack-<cloud>` в каждом namespace заказа. Формат Secret такой же, как у
provider-openstack: JSON config в ключе `config`. Значения не добавляют в Helm values.

В файле `storage-values.yaml` перечислите разрешённые подключения и проекты:

```yaml
clouds: [ru-msk, ru-spb]
projectNamespaces: [my-project]
```

Из комплекта gator-openstack-storage установите самостоятельный release:

```sh
helm upgrade --install gator-openstack-storage charts/gator-openstack-storage \
  --kubeconfig "$KUBECONFIG" -n gator-openstack-storage --create-namespace \
  -f storage-values.yaml --wait
oc --kubeconfig "$KUBECONFIG" -n gator-openstack-storage get deployment
oc --kubeconfig "$KUBECONFIG" -n my-project get volumesnapshots.storage.gatorstack.dev
```

Для каждой области chart создаёт Role только на снимки/status, чтение исходного
VolumeV3 и перечисленных ProviderConfig/Secrets. Оператор не меняет spec/status
исходного диска. Один replica и Recreate исключают параллельные штатные запуски;
resourceVersion/CAS защищает захват операции. При обновлении CRD примените его
отдельно: Helm автоматически не обновляет CRD из каталога `crds/`.

При удалении компонента сначала удалите или сохраните все его снимки по принятой
политике. Удаление CRD до завершения finalizers может оставить внешние ресурсы.
Не удаляйте finalizer при неизвестном исходе POST. Для восстановления сравните
UID CR с Cinder metadata `gator_cr_uid`; подмена внешнего ID другого снимка
отклоняется оператором.

## Зависимости и установка

Нужны Crossplane 2, provider-openstack с namespaced MR и credentials каждого
подключения. Gator Dashboard не использует cloud credentials для пользовательских
CRUD-запросов: он обращается к Kubernetes с идентичностью пользователя.
Crossplane provider и отдельная синхронизация каталога используют свои Secrets.

Поставка содержит chart `gator-openstack` для подключений и синхронизации
каталогов. В namespace заказа и namespace каталога должны существовать Secrets
`openstack-<connection>` с ключом config. Их создаёт оператор из своей системы
секретов. Не помещайте значения credentials в Helm values или ProductPage.

Пример values для интеграции:

```yaml
iaas:
  enabled: true
  clouds: [ru-msk, ru-spb]
  catalogNamespace: gator-iaas-catalog
  projectNamespaces: [demo-development]
  catalogReaderSubjects:
    - kind: Group
      apiGroup: rbac.authorization.k8s.io
      name: platform-consumers
```

Из каталога полученной поставки, после настройки целевого kubeconfig:

```sh
oc --kubeconfig "$KUBECONFIG" config view --minify -o jsonpath='{.clusters[0].cluster.server}'
helm upgrade --install gator-openstack providers/openstack/chart \
  --kubeconfig "$KUBECONFIG" --namespace crossplane-system \
  -f openstack-values.yaml --wait
```

Namespaces проектов должны существовать и содержать Project. Chart создаёт
namespace каталога; если его заранее создал другой инструмент, согласуйте
владение Helm перед установкой. ProviderConfig создаются только в перечисленных
namespace. Чтобы заказывать в другом проекте, сначала добавьте его в
projectNamespaces, установите Secret и права пользователя; наличие пункта IaaS
само по себе не создаёт подключение.

Перед первым заказом проверьте подключение именно в namespace выбранного проекта:

```sh
oc --kubeconfig "$KUBECONFIG" -n demo-development get providerconfigs.openstack.m.crossplane.io
oc --kubeconfig "$KUBECONFIG" -n demo-development get secret openstack-ru-msk openstack-ru-spb
```

Для каждого облака из `iaas.clouds` должны существовать ProviderConfig и Secret,
на который ссылается `spec.credentials.secretRef`. Команда `get secret` без
вывода YAML/JSON показывает только метаданные. Повторите проверку для каждого
namespace из `iaas.projectNamespaces`.

Если в conditions заказа появляется `ProviderConfig "ru-msk" not found`, проверьте
namespace заказа: namespaced ProviderConfig другого проекта ему недоступен.
Добавьте namespace в values интеграции, установите его connection Secrets и
повторите `helm upgrade`. Уже созданные CR Crossplane повторно обработает сам;
пересоздавать VM или SSH-ключ для устранения этой ошибки не нужно.

Product, ProductResource и ProductPage поставляются через `catalog.products`,
`catalog.resources` и `catalog.pages` отдельного chart products/iaas/chart
из репозитория gator-products. Массивы Helm заменяются
целиком: сохраняйте ранее установленные элементы каталога при добавлении IaaS.
При обновлении сначала примените CRD из комплекта Dashboard: Helm сам не
обновляет существующие CRD из директории crds.

## Каталоги OpenStack

CronJob iaas-catalog-sync каждые пять минут читает flavors, активные образы, типы Cinder и
сети для каждого подключения. Он публикует FlavorV2, ImageV2, VolumeTypeV3 и NetworkV2 в
общем namespace с managementPolicies Observe; эти объекты не создают и не
изменяют предложения во внешнем облаке. ProviderConfig задаётся для каждого
подключения отдельно. Синхронизация использует application credentials.

Каталожный объект содержит labels iaas.gatorstack.dev/cloud и
iaas.gatorstack.dev/published. Lookup пересекает фильтр публикации, выбранное
облако и поиск. Исчезнувшее предложение снимается с публикации после успешного
чтения источника. Ошибка API не превращается в пустой каталог: Job завершается
ошибкой и сохраняет последнюю успешную копию. При диагностике проверяйте время
последнего успешного Job: сохранённые предложения могут быть устаревшими.

```sh
oc --kubeconfig "$KUBECONFIG" -n gator-iaas-catalog get cronjob,jobs
oc --kubeconfig "$KUBECONFIG" -n gator-iaas-catalog get flavorv2s.compute.openstack.m.crossplane.io
oc --kubeconfig "$KUBECONFIG" -n gator-iaas-catalog get imagev2s.images.openstack.m.crossplane.io
```

Job выводит только имя подключения, количество объектов и безопасную причину
ошибки. Значения credentials и ответы аутентификации в логи не попадают.

## Права

Пользователю нужны доступ к Project, чтение каталога Dashboard и разрешения
на MR в namespace заказа. Роли iaas.viewer/editor/owner подключаются через
обычный каталог ролей. Чтение общего namespace назначается отдельно.
См. [RBAC общих справочников](rbac.md#общие-справочники-flavors-и-images).

Форма передаёт identity выбранного объекта: имя, namespace, UID и resourceVersion.
Перед созданием сервер повторно читает объект как пользователь и проверяет
scope, labels и версию. OpenStack ID извлекается из проверенного объекта,
а не принимается свободным полем формы. При конфликте обновите каталог и
повторите выбор. Все mutations требуют защиты CSRF.

## Границы текущего режима

Исполнение Direct обеспечивает проверку входной JSON Schema, разрешённых
mappings, выбранных ссылок и Kubernetes RBAC. Изменение и удаление используют
UID/resourceVersion; уменьшение диска через GrowOnly отвергается. Создание
с тем же именем возвращает конфликт вместо второго CR. Параметризованные действия
дополнительно сохраняют ActionInvocation и защищают создание связанных CR от
повторов; новый requestId означает новое подтверждение.

Полный workflow/approval, агрегатные квоты с reservations, интегрированный
заказ с биллингом и импорт существующих VM в этот режим не входят. Контракт с
Gated или quotaBindingRef не исполняется как Direct. Запрет использования flavor
при прямой записи CR требует отдельного admission/gate: UI-фильтр не заменяет
такой контроль. Гарантии tenant isolation зависят также от OpenStack project,
на который ограничены credentials каждого ProviderConfig. Для независимых
клиентов выдавайте отдельные OpenStack projects и credentials.

Перезагрузка, multiattach/force detach, расписания снимков, резервное копирование,
serial console, метрики и полный журнал операций требуют исполнительных
контрактов и соответствующих источников данных. Текущая «Диагностика» показывает
conditions Crossplane, а не историю операций. Не добавляйте кнопки с такими
названиями без работающего источника и обработчика операции.

## Окна управления ВМ и диском

**Запустить** и **Остановить** открывают подтверждение поверх карточки ВМ:
проверьте имя и облако, затем подтвердите действие или нажмите **Отменить**.
После подтверждения карточка показывает фактическое состояние через watch;
дождитесь «Работает» или «Остановлена». Перед штатной остановкой сохраните работу
в гостевой ОС. Диски сохраняются.

**Увеличить размер** открывает окно с текущим размером диска и полем нового
размера в GiB. Уменьшение запрещено сервером. После операции дождитесь нового
размера в карточке; при необходимости расширьте раздел и файловую систему в ОС.

**Создать снимок** открывает параметры снимка для выбранного диска: имя,
необязательные описание и метки. Облако и размер источника видны в окне.
После подтверждения открывается карточка нового снимка; дождитесь готовности.
Снимками управляет отдельный оператор VolumeSnapshot, установленный вместе
с интеграцией хранилища, а ВМ и дисками — стандартные GVK Crossplane.

Создание диска из снимка сохраняет регион источника и проверяет зону. В каталоге
регионального LVM выберите зону исходного диска: его snapshot находится в
соответствующем storage backend. Имя зоны переносится через metadata снимка;
сервер повторно проверяет выбор перед созданием VolumeV3.

При ошибке окно сохраняет ввод. Пока запрос выполняется, повторное подтверждение
недоступно. Отмена и крестик закрывают окно без изменения ресурса.

### Каталог образов и форма заказа

Форма ВМ разделена на общие сведения (имя, описание, метки), расположение,
образ, загрузочный диск, вычисления, сеть и доступ. Метки редактируются плашками.
Поиск конфигураций, типов диска и других справочников находится внутри списков.
Нулевой локальный диск не отображается в описании конфигурации.

Образы остаются штатными Observe-only `ImageV2` Crossplane. Синхронизация
OpenStack публикует аннотации `catalog.gatorstack.dev/title`, `group`, `variant`,
`description`, `icon`. По умолчанию берутся Glance name, os_distro, os_version,
description и свойства `gator_title`, `gator_group`, `gator_variant`,
`gator_description`, `gator_icon`. В chart провайдера `iaas.imageCatalog`
позволяет переопределить эти пять значений по UUID образа или его имени
(UUID имеет приоритет). Настройка применяется при очередной синхронизации,
не создаёт новый образ и не меняет работающие ВМ.

Сам способ отображения задаёт универсальный [элемент каталога](resource-pages.md#каталог-карточек-из-json-schema)
в JSON Schema: GVK, scope, фильтры и пути к аннотациям можно заменить манифестом.

### Иконка образа в списке ВМ

Перед именем ВМ показывается иконка образа, выбранного при заказе. Манифест
IaaS копирует `catalog.gatorstack.dev/icon` и `title` из выбранного `ImageV2`
в аннотации `iaas.gatorstack.dev/image-icon` и `image-title` ресурса `InstanceV2`.
Колонка имени читает эти аннотации через общие `iconPath` и `iconAltPath`.

Для ВМ, созданных до включения этой настройки, OpenStack observer заполняет
отсутствующие аннотации по ID загрузочного образа и ProviderConfig того же
облака. Это не изменяет spec/status CR или внешнюю ВМ. Существующие снимки
иконки сохраняются. Для неизвестного источника (например, загрузки из
существующего тома без идентификатора исходного образа), неоднозначного
каталога или отсутствующей иконки используется нейтральный значок.


Справочники типов дисков, конфигураций ВМ и образов используют проверку
содержимого выбранных CR. Обновление служебной отметки синхронизации Crossplane
не мешает созданию диска или ВМ. Изменение выбранных характеристик требует
проверить обновлённые варианты и подтвердить создание ещё раз; введённые поля
сохраняются.
