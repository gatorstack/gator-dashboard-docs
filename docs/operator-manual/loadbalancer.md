# Балансировщик L4

Сервис распределяет TCP- и UDP-трафик между IPv4-адресами приложений.
Он находится в категории **Infrastructure** и работает через OpenStack Octavia
Amphora. Консоль управляет Kubernetes API продукта; Crossplane согласует
балансировщик, обработчики, пулы, цели, проверки состояния и внешний адрес.

Отображаемое имя хранится в `spec.name` основного XR. Техническое
`metadata.name` и ссылки по UID остаются стабильными при его изменении.
У прежних XR без `spec.name` консоль показывает техническое имя; задайте
пользовательское имя через форму редактирования, не переименовывая Kubernetes
объект и не пересоздавая инфраструктуру.

## Подготовка

Для таблицы интерфейсов в пакете L4 0.5 нужен Dashboard 0.25.23 или новее:
сначала обновите консоль, затем пакет продукта. Источник — проектные PortV2
VPC с наблюдаемыми fixed IPs. Роль L4 viewer включает чтение этих интерфейсов;
Composition получает read-only доступ к PortV2/SubnetV2. Внешние интерфейсы,
для которых нет проектного PortV2, сначала должны быть представлены в VPC API.

Администратору нужны Crossplane v2 с namespaced XR, provider-openstack с
namespaced API Octavia и Neutron, работающий Octavia Amphora и внешняя сеть
Neutron. В namespace каждого проекта должны существовать свои ProviderConfig
и application credential выбранного региона. Сервисные credentials не выдаются
пользователям и не копируются в заказы.

Установите [OpenStack-интеграцию](iaas.md). Lifecycle выполняет native provider
Crossplane. Отдельный наблюдатель состояний Octavia не требуется.
Для метрик нужен [мониторинг](monitoring.md), установленный provider-kubernetes
с InjectedIdentity и native поддержка Octavia `PROMETHEUS` listener.

В комплекте `gator-products` подготовьте профиль:

```yaml
regions:
  region-one:
    externalNetwork: external-region-one
```

Установите пакет в namespace каталога Dashboard:

```sh
helm dependency build --skip-refresh products/loadbalancer/chart
helm upgrade --install gator-loadbalancer products/loadbalancer/chart \
  --kube-context "$GATOR_CONTEXT" -n gator-dashboard \
  -f loadbalancer-values.yaml --wait
kubectl --context "$GATOR_CONTEXT" wait \
  xrd/networkloadbalancers.loadbalancer.gatorstack.dev \
  xrd/targetgroups.loadbalancer.gatorstack.dev \
  --for=condition=Established --timeout=180s
kubectl --context "$GATOR_CONTEXT" wait \
  function/gator-l4-go-templating function/gator-l4-auto-ready \
  --for=condition=Healthy --timeout=180s
```

Не принимайте заказы до готовности XRD и функций. Primary CRD принадлежат XRD:
не удаляйте их при обновлении пакета. При удалении Helm-пакета определения XRD
сохраняются. Новая установка не требует смены владельцев существующих releases.

## Создать балансировщик

1. В VPC подготовьте подсети проекта и маршруты к приложениям. В группах
   безопасности backend разрешите трафик и health checks из сети балансировщика.
2. Откройте **Балансировщик L4 → Целевые группы**. Задайте имя и регион,
   отметьте интерфейсы и IP-адреса в таблице. В ней показаны имя ВМ, интерфейс,
   IP и подсеть. Можно выбрать несколько целей сразу, включая интерфейсы
   разных подсетей одного региона. Подсеть определяется автоматически по
   выбранному интерфейсу. Дождитесь готовности группы.
3. Если нужен сохраняемый внешний адрес, используйте свободный адрес
   из общего списка **Compute**. Это существующий FloatingipV2 проекта,
   отображаемый также в VPC; отдельного списка адресов у L4 нет. Для автоматического адреса этот шаг не требуется.
4. Откройте **Балансировщики → Создать**. Задайте имя, описание, метки, регион,
   VIP-подсеть и тип. Внутренний балансировщик получает адрес выбранной подсети.
   Внешний дополнительно использует Floating IP: автоматически либо из списка
   зарезервированных адресов того же проекта и региона.
5. Добавьте обработчики. Для каждого укажите имя, TCP/UDP, входной порт,
   целевой порт, группу и проверку состояния. Например: TCP 80 → 8080,
   HTTP-проверка на порту 8081 по пути `/health`.
6. Настройте timeout, interval и пороги успешных/неуспешных проверок.
   Timeout должен быть меньше interval. HTTP ожидает код 200; TCP проверяет
   соединение. Проверка может использовать порт, отличный от целевого.
7. При необходимости включите защиту от удаления балансировщика и создайте ресурс.
   Дождитесь **Активен** и отдельно проверьте трафик из клиентской сети.

Протокол и порт обработчика должны образовывать уникальную пару. Алгоритм
распределения — round robin. При TCP/UDP TLS проходит до приложения; TLS
termination, HTTP-маршрутизация и отдельная DDoS-защита в этот сервис не входят.
В лаборатории внешние адреса могут быть доступны только через VPN: наличие
Floating IP само по себе не означает доступ из интернета или физическую HA.

## Состояние и изменения

Карточка показывает адреса, условия Crossplane, обработчики и цели.
**Активен** означает применение конфигурации: необходимые ресурсы созданы,
наблюдаемые параметры соответствуют заказу. Доступность приложения и
мониторинга не влияет на этот статус. **Создаётся** означает согласование,
**Ошибка настройки** — ошибку managed resource/provider.

Во вкладке **Целевые ресурсы** таблица мониторинга показывает каждую TCP-цель:
**Да** — доступна, **Нет** — недоступна. Для UDP и при отсутствии метрик за
последние 90 секунд — **Нет данных**. Проверьте приложение, health endpoint,
маршруты и SG, если цель недоступна. Ready целевой группы подтверждает адреса
и ссылки; успешный заказ сам по себе не гарантирует ответ приложения.

Редактируются описание, метки, обработчики и состав целевой группы. Защита
от удаления доступна только у балансировщика.
Обновление группы передаётся всем использующим её балансировщикам. Регион,
тип, VIP-подсеть и режим выделения адреса выберите при создании; эти настройки
неизменяемы. Изменение портов/протокола или удаление обработчика может прервать
соединения. Успешная запись XR означает принятие заказа, затем дождитесь
согласования Crossplane. Здоровье приложения проверяйте отдельно.

Ссылки закреплены по UID, namespace и региону. Пересоздание CR с прежним именем
не переносит на него существующий заказ автоматически. Пока зависимость
недоступна или её identity не совпадает, Composition сохраняет действующие
ресурсы и сообщает ошибку синхронизации. Подробности видны в условиях карточки.

## Удаление и доступ

Перед удалением балансировщика отключите его защиту, если она включена.
У целевых групп такой защиты нет; прежний `spec.deletionProtection` игнорируется,
включая значение `true`. Сначала удалите использующий
балансировщик, затем ненужные целевые группы и резервные адреса. Crossplane
Usage блокирует удаление используемой подсети, группы и резервного адреса;
после удаления потребителя ранее отклонённый запрос на удаление внешней
зависимости автоматически не повторяется.

Автоматический адрес отображается в общем Compute списке и удаляется вместе
с балансировщиком. Выбранный из общего Compute списка
`FloatingipV2` сохраняется: удаляется только его ассоциация с VIP. Один
резервный адрес может использоваться одним балансировщиком одновременно.

Пакет поставляет `loadbalancer.auditor`, `.viewer`, `.editor`, `.owner`.
Назначайте их обычными RoleBinding проекта. Editor управляет заказами; чтение
подсетей нужно для формы выбора. Права проекта не дают доступ к Secret подключения
или к ресурсам чужого проекта. Операции отображаются в истории продукта.

## API

Оба primary API — namespaced XR группы
`loadbalancer.gatorstack.dev/v1alpha1`:

| Kind | Назначение |
| --- | --- |
| NetworkLoadBalancer | VIP, адрес, обработчики, группы и health checks |
| TargetGroup | Переиспользуемые адреса приложений с pinned ссылками на подсети |

Для GitOps получите текущие UID и resourceVersion подсети/группы в своём
namespace. Ссылка содержит `name`, `namespace`, `uid`, `resourceVersion`.
Не копируйте UID из другого окружения. Формы консоли заполняют эти поля при
выборе из каталога. Дочерние MR изменяйте через основной XR; прямые изменения
могут быть восстановлены Composition.

Выбор общего адреса допускает только свободный, готовый ресурс того же проекта
и региона с managementPolicies без LateInitialize. Владелец адреса сохраняется.
Привязка использует общий с Compute singleton; при одновременном назначении
ВМ и балансировщику второй потребитель получает конфликт, а текущая привязка
не переносится. Общий список показывает ресурс-потребитель; отвязку от L4
выполняйте удалением соответствующего балансировщика.


## Подключить метрики целей

Добавьте в профиль пакета:

```yaml
monitoring:
  enabled: true
  backend: platform
  port: 8088
  scraperCIDRs: [192.0.2.10/32]
  providerConfig: gator-l4-local
  kubernetesServiceAccount: existing-provider-kubernetes
```

Замените CIDR на фактический source IP доверенного VMAgent, включая SNAT,
а ServiceAccount — на identity уже установленного provider-kubernetes в
crossplane-system. Пакет создаёт отдельный ClusterProviderConfig и выдаёт этой
identity права на MetricSource/MetricOwnershipPolicy. Сервисный credential
в проект не копируется. TCP-порт мониторинга резервируется в форме и API.

Composition создаёт native `PROMETHEUS` listener с `allowedCidrs`.
Для External используется основной Floating IP из общего Compute списка.
Для Internal создаётся отдельный служебный Floating IP и native Neutron
port forwarding только TCP 8088 → VIP:8088. Рабочие порты остаются внутренними;
служебный адрес потребляет квоту Floating IP, не появляется как свободный
Compute-адрес и удаляется вместе с заказом. В Neutron должны быть включены
`port_forwarding` service plugin и L3 extension. В Kolla это
`enable_neutron_port_forwarding: "yes"`; применяйте штатный reconfigure Neutron.

В профиле Dashboard выдайте monitoring-контроллеру чтение PoolV2:

```yaml
monitoring:
  sourcePermissions:
  - apiGroups: [lb.openstack.m.crossplane.io]
    resources: [poolv2s]
    verbs: [get, list, watch]
  backend:
    sourceNetworkPolicy:
      ipBlocks: [198.51.100.0/24]
      ports: [8088]
```

Дополните существующие списки, сохранив прежние источники. В `ipBlocks` укажите
пулы адресов endpoint, в `ports` — порт мониторинга. Эта политика запрещает
проектным pod прямой scrape защищённых адресов/портов; остальные порты остаются
доступны. Порт мониторинга внутри указанных CIDR следует выделить только для
этой цели. Убедитесь, что CNI исполняет NetworkPolicy и пользователь не может
менять системную политику. Примените защиту до создания PROMETHEUS listener.

Проверьте MetricSource/MetricOwnershipPolicy с именем `l4-<UID без дефисов,
первые 24 символа>`, native VMStaticScrape и данные через gateway проекта.
Ownership использует UUID native пула и регион. Endpoint/IP и статический
resource_uid не считаются доказательством владельца. Native PoolV2 и Object
bridge защищаются admission/RBAC. TCP-метрики Octavia не покрывают UDP.

## Графики в карточке балансировщика

Вкладка **Мониторинг** поставляется JSON Schema пакета L4 и использует
проектный gateway. Отдельного приложения или экспортера для неё не требуется.
Источник — уже собираемые `octavia_pool_*` и `octavia_member_status`,
владение данными подтверждается native UUID пула и регионом. CPU, память
Amphora и служебный listener не входят в эти графики.

Показываются трафик, активные сессии, новые сессии в секунду, ошибки
соединений/ответов backend, очередь и доступность TCP-целей. Значения
агрегируются по прикладным пулам текущего балансировщика. Счётчики
преобразуются в скорость с учётом выбранного периода. Наблюдения старше
90 секунд исключаются; отсутствие рядов не заменяется нулём. Для UDP
эти метрики не публикуются.

Для просмотра назначьте в проекте `monitoring.auditor` либо
`monitoring.viewer`. Роли L4 сами по себе не открывают метрики. При пустых
графиках проверьте выбранный период, права, MetricSource/ownership policy
и доступ scraper к PROMETHEUS endpoint. Недоступность мониторинга не меняет
успешность заказа.

## Сохранить прежние журналы

После перехода новые состояния читаются только из мониторинга. При обновлении
остановите прежний producer и дождитесь доставки очереди, затем отключите
старый Kafka ingestion. `logging.enabled: true` сохраняет LogSource и вкладку
для чтения уже принятых событий. Доступ — `logging.viewer`, retention — 30 дней.
Удалять историю VictoriaLogs при переходе не требуется.

Octavia 2025.2 маркирует pool как `<pool UUID>:<listener UUID>`. Composition
публикует эту identity в защищённой аннотации native PoolV2; ownership policy
читает её JSON Pointer. Источник identity — фактически созданные native IDs.

Для чтения таблицы метрик нужны права на ProjectMonitoring/project: назначьте
monitoring.auditor либо monitoring.viewer в проекте. Продуктовая роль L4 сама
по себе не открывает все метрики проекта.


NetworkPolicy применяется CNI асинхронно. При сетевой проверке дождитесь
применения политики к тестовому pod: само наличие CR не подтверждает фильтрацию.
Стандартные роли каталога, включая owner, не дают права создавать произвольные
pod или hostNetwork-нагрузки. Для проектов с такими дополнительными правами
нужна отдельная изоляция исходящего трафика scraper; один node-SNAT CIDR не
отличает доверенный VMAgent от остальных нагрузок узла.


## Подключить пользовательские группы безопасности

Нужны Octavia API 2.29+ с поддержкой `vip_sg_ids`, namespaced Neutron SG API и
установленные provider-kubernetes/provider-ansible. Добавьте в профиль L4:

```yaml
securityGroups:
  enabled: true
  providerConfig: gator-l4-local
  kubernetesServiceAccount: existing-provider-kubernetes
  ansibleServiceAccount: existing-provider-ansible
```

Используйте ServiceAccount существующих providers в crossplane-system; пакет
не переустанавливает общие providers. У provider-ansible должен быть доступ
к исходным проектным application credential Secret. Пакет выдаёт ему чтение
primary XR для защиты от устаревших запусков. Credentials читаются по исходным
ссылкам; токены и ответы API скрыты `no_log`.

Формы показывают готовые SG того же проекта/региона. Composition повторно
проверяет identity и создаёт Usage. Стандартный AnsibleRun задаёт `vip_sg_ids`
через Octavia; старое `LoadbalancerV2.securityGroupIds` меняет только Neutron
VIP-порт и для этой операции не используется. VIP, внешний адрес и основной
cloud ID сохраняются. Пустой список возвращает автоматические правила.
Изменения правил backend-ВМ администратор выполняет отдельно.

Octavia не допускает пользовательские SG вместе с `listener.allowed_cidrs`.
Поэтому перед сменой SG Composition сначала останавливает endpoint метрик,
убирает это поле, применяет SG, затем включает endpoint снова. Для custom SG
создаётся служебная группа с доступом к порту метрик только из scraperCIDRs.
При возврате к автоматическому режиму восстанавливается `allowed_cidrs`.
Правила разных SG складываются: пользовательское разрешение всех портов для
общих сетей также откроет порт метрик. Оставляйте его только доверенным
scraper-источникам. Служебные SG и исполнения защищены от клиентских изменений.


Читаемые имена ВМ и подсетей для таблицы публикует VPC adapter из OpenStack
integration 0.3.8+. Он сопоставляет InstanceV2 по cloud deviceId, а каждый IP
PortV2 — по наблюдаемым subnet IDs, network ID и CIDR в текущем проекте/регионе.
Аннотации `vpc.gatorstack.dev/instance-title` и `vpc.gatorstack.dev/ip-subnets`
содержат только подписи. Неоднозначные сопоставления не показываются.
Adapter не меняет spec/status интерфейса и не обращается к Octavia. Отсутствие
подписи подсети не означает недоступность backend; его состояние берётся
из мониторинга.
