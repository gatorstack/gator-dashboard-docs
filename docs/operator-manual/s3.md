---
title: Установка S3-продукта
---

Пакет S3 использует внешний Ceph RGW и [provider-radosgw](radosgw-provider.md).
Данные, MON/MGR/OSD/RGW остаются на внешних узлах. В Kubernetes работают
Crossplane и его провайдер; отдельного lifecycle оператора S3 и workload на бакет нет.
Формы и поведение задают Product/ProductResource/ProductPage и JSON Schema.

## Предварительные условия

Установите провайдер, настройте доступный по HTTPS S3 endpoint и регион подписи.
Для выбора HOT/COLD заранее создайте backend placement targets `hot`/`cold`,
у которых STANDARD направлен в соответствующие data pools. Сам Bucket CR
не имеет поля LocationConstraint. Установка создаёт два управленческих root
подключения одного Ceph Account с разными User.defaultPlacement.

Нужны Kubernetes с ValidatingAdmissionPolicy v1, административный доступ,
Helm, Python с зависимостями из scripts/requirements.txt пакета интеграции
и oc. Подготовьте вне Git файл credentials JSON с endpoint/access_key/secret_key
для отдельного RGW provisioning user с Admin Ops capabilities accounts/users/buckets.
Файл должен иметь режим 0600. Не используйте эти credentials в приложениях.

## Подготовка подключений

В поставке gator-products находятся `providers/radosgw/chart` и
`providers/radosgw/scripts/bootstrap-projects.py`. Установите admission, namespaced XRD S3Bucket и Composition:

```sh
helm upgrade --install gator-radosgw ./providers/radosgw/chart \
  --kube-context YOUR_CONTEXT -n gator-s3-system --create-namespace --wait
```

Создайте профиль без credentials:

```yaml
expectedServer: https://your-kubernetes-api.example.org:6443
systemNamespace: gator-s3-system
endpoint: https://s3.example.org
region: us-east-1
title: Ceph S3
projectNamespaces:
  - application-project
```

`region` должен соответствовать API-имени zonegroup (`api_name`) RGW. Внутреннее
имя zonegroup может отличаться. Для стандартной настройки используйте us-east-1.
После изменения региона повторите bootstrap, чтобы обновить публичные каталоги;
при необходимости обновите аннотацию s3.gatorstack.dev/region существующих CR.
Изменение этих отображаемых данных не требует выпуска новых ключей.

В namespace должен существовать Project с именем project. Выполните bootstrap
с явным kubeconfig и защищённым файлом:

```sh
python3 providers/radosgw/scripts/bootstrap-projects.py \
  --kubeconfig /secure/kubeconfig \
  --profile s3-profile.yaml \
  --admin-credentials-file /secure/rgw-provisioning.json
```

Скрипт проверяет API server и endpoint, создаёт native Account/User/UserCaps/AccessKey
в служебном namespace, ждёт готовности ключей и создаёт private provider credentials.
В проекте появляются только публичные каталоги подключений, классов и прав.
ClusterProviderConfig выбирает служебный Secret без его копирования в проект.
Повторное применение сохраняет ключи; несовместимое владение останавливает работу.

Для нового проекта добавьте namespace в профиль и повторите bootstrap.
Отдельный контроллер автоматического подключения проектов не устанавливается.
После административной ротации root-ключа повторите bootstrap, чтобы обновить
проекцию credentials. Удалённые из профиля аккаунты и данные автоматически не удаляются.

## Каталог и права

Подключите `products/s3/chart` в существующую сборку Gator. Для новой самостоятельной
установки пакета можно использовать отдельный release в namespace консоли:

```sh
helm dependency build products/s3/chart
helm upgrade --install gator-product-s3 products/s3/chart \
  --kube-context YOUR_CONTEXT -n gator-dashboard --wait
```

Если объекты уже принадлежат umbrella release, обновляйте его; не создавайте
другой Helm release поверх тех же Product и ClusterRole. Dashboard требует
версию 0.12.1 для вывода технического имени над заголовком; connection-secret
outputs и finalMappings доступны с 0.11.1.

Роли s3.auditor/viewer читают ресурсы и каталоги. s3.editor создаёт/изменяет,
а s3.owner также удаляет. В текущем варианте editor/owner имеют get Secret в
namespace проекта. Это более широкое право, чем чтение одного ключа; точечные
resourceNames/отдельные credential-роли можно назначить дополнительно средствами
Kubernetes. Административные Secret всегда остаются в служебном namespace,
доступ к нему потребителям продукта не выдаётся.

Admission ограничивает подключения namespace UID проекта, префикс имён бакетов,
прикладные IAM identities, разрешённые S3 policy и выходные Secret names.
Проверки действуют при прямой записи native CR, а не только через формы.
Не разрешайте потребителям изменять namespace labels, служебные ConfigMap,
ClusterProviderConfig или admission policy.

## Эксплуатация

Основные CR: Bucket, AccountUser, AccountAccessKey и AccountUserPolicy.
Учётка создаётся без S3 прав. Назначение AccountUserPolicy открывает конкретный
бакет и разрешает s3:ListAllMyBuckets для аккаунта проекта; ключи выдаёт
AccountAccessKey через connection Secret. Список содержит названия всех бакетов
аккаунта независимо от персонального доступа к содержимому. Дополнительный
statement не выдаёт s3:ListBucket/GetObject/PutObject на другие бакеты. Сохраняйте Secret
в backup вместе с CR и проверьте восстановление по руководству провайдера.

Запись истории о выдаче ключа содержит access/reveal и identity CR, без Secret data.
Просмотр выполняется с токеном пользователя и требует get конкретного Secret.
Ready и принятие запроса различаются: проверяйте conditions, состояние backend
и реальные S3 операции. Для диагностики сначала сверьте выбранный кластер.

Для лимита отдельного account-owned бакета установите provider-radosgw rc.16 или
новее и задайте `ProviderConfig.spec.bucketQuotaUserID` (либо ClusterProviderConfig)
как RGW UID пользователя того же аккаунта. Bootstrap продукта заполняет UID
соответствующей HOT/COLD root identity; capabilities и ключи не меняются.
Провайдер исправляет только индивидуальный quota PUT с Account ID вместо uid,
сохраняя авторизацию и TLS. Пустая настройка сохраняет upstream-поведение.
Не заменяйте этот лимит общей квотой аккаунта: у неё другой scope.

Каталог S3 0.4.1 требует Dashboard 0.21.3+ и использует `s3.gatorstack.dev/v1alpha1 S3Bucket`. Нужен
Crossplane v2 с namespaced XR, включёнными Usages и RBAC manager. Chart
интеграции 0.2.2 устанавливает XRD, Composition `gator-s3-bucket` и стандартные
функции go-templating 0.13.2 / auto-ready 0.7.3. Их registry можно заменить
параметрами `composition.goTemplatingPackage` и `composition.autoReadyPackage`.
Дождитесь `Installed=True`, `Healthy=True` у обеих Function и `Established=True`
у XRD, прежде чем устанавливать каталог.

Форма сохраняет один XR. `spec.forProvider.bucketQuota` содержит enabled,
maxSize в байтах и maxObjects; `spec.publicAccess` — три разрешения чтения.
Непустой `spec.policy` задаёт произвольный JSON document вместо переключателей.
Composition создаёт native Bucket с именем XR, затем BucketPolicy и namespaced
Usage для порядка удаления. BucketPolicy не появляется до Ready/Synced
собственного Bucket: ошибка существования бакета не открывает чужие данные.
Оба native CR и Usage находятся в namespace проекта. Ошибки отражаются в
`status.managedConditions`; `status.atProvider` содержит наблюдаемые поля Bucket.
Native Bucket/Policy доступны проектным ролям для чтения, запись идёт через XR.

Учётки, ключи и их Secret остаются отдельными namespaced native ресурсами.
Composition не копирует root credentials и не выпускает новые ключи бакета.
CORS, lifecycle, website и назначения доступа сохраняют свои CR и вкладки.
Удалению XR предшествует удаление таких независимых настроек и назначений.
`forceDestroy` запрещён: непустой бакет не очищается автоматически.
Удаление XR выполняется с propagationPolicy Foreground: XR остаётся видимым,
пока не удалены его дочерние CR. В диагностике доступны условия самого Crossplane
и read-only native Bucket; ошибка непустого бакета остаётся доступной. После
очистки бакета удаление продолжится автоматически.

### Перенос действующих бакетов под Composition

Не удаляйте native CR и не используйте повторный Create/Import для Ceph bucket.
Сначала установите chart интеграции с XRD и проверьте функции. Затем сохраните
закрытый снимок и выполните перенос с явной проверкой кластера:

```sh
python3 providers/radosgw/scripts/migrate-buckets-to-composition.py plan \
  --kubeconfig /secure/kubeconfig --expected-server https://kubernetes.example.org:6443 \
  --namespace application-project --snapshot /secure/s3-composition-snapshot
python3 providers/radosgw/scripts/migrate-buckets-to-composition.py apply \
  --kubeconfig /secure/kubeconfig --expected-server https://kubernetes.example.org:6443 \
  --snapshot /secure/s3-composition-snapshot
```

Plan сохраняет только CR бакетов и связанных настроек, без Secret.
Apply создаёт paused XR с прежним именем, передаёт controller reference,
заполняет `spec.crossplane.resourceRefs`, перепривязывает UID отношений и снимает
паузу. UID native Bucket, внешний ID, tenant, ключи и данные не меняются.
Существующая JSON policy переносится целиком в `spec.policy`.
Скрипт отказывается от изменившегося spec/UID или чужого controller. При частичном
сбое исправьте причину и повторите apply с тем же снимком; не удаляйте paused XR,
которому уже переданы CR. Снимок содержит операционные метаданные: храните его
в закрытом каталоге вне Git.

Проверьте Ready/Synced XR, неизменность native UID и Ceph ID, настройки и объекты.
После этого обновите каталог до S3 0.4. Биллинг продолжает учитывать native Bucket
по прежнему UID; второй MeteringPolicy для XR создавать не нужно. Логи получают
bucket/tenant из отражённого status XR. Смена GVK не переносит старые записи
истории автоматически; сохранённая история native CR остаётся с прежней identity.

## Обновление существующих назначений

Новые назначения S3 0.1.5 содержат право списка проекта. Сначала обновите chart
интеграции `gator-radosgw` до 0.1.1 или новее, затем пакет каталога. Admission
сохраняет поддержку старого шаблона без списка. Для существующих назначений
запустите миграцию из комплекта gator-products:

```sh
python3 providers/radosgw/scripts/enable-project-bucket-listing.py \
  --kubeconfig /secure/kubeconfig \
  --expected-server https://api.example.org:6443 \
  --namespace application-project
```

По умолчанию выполняется серверная проверка без записи. Проверьте перечень
назначений и повторите команду с `--apply`. Для нескольких проектов повторите
`--namespace`. Скрипт изменяет только известные managed AccountUserPolicy:
добавляет один statement списка, сохраняя права на бакет/объекты, владельца и UID.
Неизвестный policy или несовпадение проекта останавливает миграцию. UID и
resourceVersion проверяются атомарно; повторный запуск не меняет готовые policies.
Ключи и Secret не читаются. Дождитесь Ready/Synced и проверьте S3-клиентом как
список проекта, так и отказ на содержимое бакета без назначения.

## Граница управления

S3-продукт управляет только native Kubernetes ресурсами через GVK. Для объектных
данных приложения используют внешний S3 API по собственным ключам. Отдельный
HTTP adapter или workload для просмотра бакетов устанавливать не нужно.
Карточка бакета открывается на Обзоре; статистика из стороннего usage observer
не используется. При миграции старой установки удалите только службу просмотрщика,
её scoped identity, Secret адаптера, Ingress/Service/Certificate и usage annotations.
Данные Ceph, native CR, аккаунты и ключи сохраняйте.

## Native настройки бакета

CORS, lifecycle, website и bucket policy представлены штатными namespaced
BucketCorsConfiguration, BucketLifecycleConfiguration, BucketWebsiteConfiguration,
BucketPolicy. Admission запрещает cross-project connection и bucketRef.namespace.
Одна конфигурация каждого типа привязывается к UID бакета. Удаляйте их до бакета.
Для website включите rgw_enable_static_website и настройте отдельный
rgw_dns_s3website_name с DNS, ingress и TLS. Анонимное чтение включается явной
BucketPolicy. CORS сам по себе доступ не открывает. Lifecycle transitions и
expiration исполняются периодически самим RGW.

## Редактирование бакета и наблюдаемые значения

Лимит меняет `Bucket.spec.forProvider.bucketQuota.enabled/maxSize`; переключатель
не изменяет квоты других бакетов. Старый отключённый лимит с maxSize=-1 получает
безопасное начальное значение размера только в форме; CR не меняется до сохранения.
Поле обзора читает status.atProvider с fallback на spec и форматирует байты.

На странице редактирования native BucketPolicy подключён через
`x-dashboard-form.relatedForms`. Сохранения параметров и доступа независимы,
каждое требует прав caller на свой GVK. Уже применённые параметры не откатываются
при ошибке политики. Оба действия используют обычные canonical операции;
политика обновляется через UpdateResource с ActionInvocation. Отсутствующая
политика создаётся CreateResource с выбранным Bucket UID, пустой Statement
закрывает публичное чтение без удаления CR. Произвольный JSON защищён schema
precondition, включая точный ARN выбранного бакета; полный редактор сохраняется.
При обновлении каталога существующие CR не переписываются.


## RGW tenant проекта

Bootstrap выделяет отдельный RGW tenant для пары namespace UID и Project UID
и создаёт внутри него native Account и HOT/COLD root User. Строка tenant имеет
форму gator_<стабильный hash UID>. Она не является числовым tenant ID мониторинга.
Служебный каталог подключений содержит tenant; credentials остаются в Secret.
BucketQuotaUserID использует полное имя tenant$user. Обычный S3-клиент со своим
ключом указывает привычное имя бакета: RGW определяет tenant из пользователя.

Tenant Account/User неизменяем. Повторный bootstrap с другой identity
останавливается и требует явной миграции. Существующие бакеты нельзя переносить
сменой поля tenant. Перед переходом выберите перенос/восстановление данных либо
явно разрешённое пересоздание с удалением содержимого. После пересоздания
получите новые ключи из native connection Secrets; старые ключи недействительны.
Непроектные legacy аккаунты и бакеты оставляйте отдельно.

При анонимном публичном доступе tenant нельзя вывести из ключа. Используйте
path-style URL с tenant:bucket; публичность по-прежнему требует явной BucketPolicy.
Для мониторинга native counters связываются по tenant, stats — по Account ID;
подробнее в [руководстве мониторинга](monitoring.md#продуктовые-интеграции).


В политиках доступа к tenanted бакетам используйте канонический ARN
`arn:aws:s3::<tenant>:<bucket>` и суффикс `/*` для объектов. Пустой account-сегмент
не даёт прикладному IAM-пользователю доступ к такому бакету. Каталог подключений
содержит arnPrefix, форма бакета сохраняет canonical bucket-arn, а формы назначений
и публичного доступа используют его декларативно. Повторный bootstrap дополняет
эти метаданные существующих managed бакетов. Admission сверяет tenant с
защищённой меткой namespace. Для individual quotas в tenant accounts требуется
provider-radosgw v0.1.0-rc.18 или новее.

### Пример S3Bucket

После bootstrap замените `gs3-project-prefix` значением connection вашего проекта
из каталога классов. Префикс имени бакета и ProviderConfig должны принадлежать
этому проекту; admission отклоняет чужие подключения.

```yaml
apiVersion: s3.gatorstack.dev/v1alpha1
kind: S3Bucket
metadata:
  name: example-bucket
  namespace: application-project
  labels:
    s3.gatorstack.dev/managed: 'true'
    s3.gatorstack.dev/connection: gs3-project-prefix
  annotations:
    s3.gatorstack.dev/title: example
spec:
  providerConfigRef:
    kind: ClusterProviderConfig
    name: gs3-project-prefix-hot
  forProvider:
    bucket: gs3-project-prefix-example
    forceDestroy: false
    versioning: 'off'
    bucketQuota:
      enabled: true
      maxSize: 53687091200
      maxObjects: -1
  publicAccess:
    readObjects: false
    listObjects: false
    readSettings: false
  policy: {}
```

Имя и подключение неизменяемы. Для закрытого доступа Composition создаёт policy
с пустым Statement. `status.bucketRef` указывает на прежний native CR; status не
содержит S3 ключи. Ключи получают у независимой учётки проекта.

Перед созданием native Bucket Composition запрашивает managed Bucket своего
namespace через RequiredResources и проверяет controller UID. Совпадение внешнего
имени у другого CR блокирует pipeline с BucketAlreadyExists без создания второго
MR. Это сохраняет защиту повторного заказа и для перенесённых бакетов с
историческим именем CR. На карточке ошибка XR видна до появления native CR.

Migration сохраняет на native Bucket label `s3.gatorstack.dev/bucket-name`.
Composition запрашивает только это имя в своём namespace, чтобы изменения
посторонних бакетов не запускали согласование всех XR проекта. При обновлении
с ранней интеграции без label сначала дополните им native Bucket, сохраняя
UID и spec, и лишь затем обновляйте Composition.
