# Защита и состав удаления

Защита от удаления — изменяемое поле самого заказа. Она предотвращает случайное
удаление, сохраняя возможность штатно выключить защиту и затем удалить ресурс.
Права Kubernetes RBAC проверяются отдельно: отключение защиты не выдаёт право delete.

## Настроить защиту продукта

ProductResource задаёт JSON Pointer к boolean-полю основного CR:

```yaml
spec:
  delete:
    enabled: true
    protectionPath: /spec/lifecycle/preventRemoval
    preview:
      inventoryPath: /status/deletionInventory
      kindLabels:
        Machine: Виртуальные машины
        Volume: Диски
```

Путь выбирает автор продукта; ядро не привязано к имени поля или GVK.
Укажите это поле в canonical форме Edit, чтобы пользователь мог выключить защиту.

При true подтверждение удаления объясняет, что сначала нужно выключить защиту
в настройках ресурса и сохранить изменения. Кнопка подтверждения недоступна.
Backend повторно читает объект и проверяет защиту независимо от браузера.
Отсутствующее или не-boolean значение блокирует удаление до уточнения состояния.

| Ответ Dashboard API | Значение |
| --- | --- |
| 422 `DeletionProtectionEnabled` | Защита включена; сначала отключите её и сохраните изменения |
| 422 `DeletionProtectionUnknown` | Состояние защиты неизвестно; обновите карточку или проверьте конфигурацию продукта |
| 403 | Не выполнена проверка прав или другая политика доступа |

Для защиты прямого Kubernetes DELETE продукт должен также установить admission
policy/webhook, проверяющий то же поле. Одна настройка protectionPath защищает
путь Dashboard и не устанавливает автоматически Kubernetes admission для произвольного API.
Не публикуйте пользователю необработанные тексты admission: они могут содержать
фрагменты конфиденциальных объектов.

## Автоматический состав заказа

В подтверждении доступен раскрывающийся список **Ресурсы заказа**. Для каждой
зависимости показаны имя, внешний ID или адрес и ожидаемое действие:
**Удалится**, **Сохранится** либо **Уточняется**.

Список не требуется вручную заполнять именами VM, дисков или IP. Источник —
наблюдаемый граф конкретного XR, а не только определение его типа XRD:

- composed resources и вложенные XR с resourceRefs;
- принадлежность дочернего объекта ожидаемому owner UID;
- стандартные Object bridge и их наблюдаемые native ресурсы;
- зависимости Usage.of, которые сами по себе не задают каскадное удаление;
- deletionPolicy и managementPolicies, определяющие сохранение внешнего объекта.

Общая библиотека gator-product предоставляет шаблон `gator-product.deletion-inventory`
для стандартной function-go-templating. Продукт подключает публикацию безопасного
состава в status XR; Dashboard читает его по inventoryPath с правами пользователя.
kindLabels меняет только подписи типов. Перечень экземпляров вычисляется автоматически.

Observe-only представление VM не считается второй VM. Если в том же графе есть
удаляемый writer того же внешнего объекта, он показан один раз как удаляемый.
Orphan и отсутствие Delete отражаются как сохранение внешнего объекта. Служебная
запись Kubernetes при этом может быть удалена: сохранение относится к управляемому
внешнему ресурсу.

Некоторые внешние зависимости не имеют отдельного CR. Для них provider observer
добавляет фактические связи в состав. Например, PostgreSQL получает ID прикреплённых
дисков и delete-on-termination из Nova; UUID исходного образа не подменяет ID диска.

Граф обходится с ограничениями глубины и количества запросов. Недоступные,
непринадлежащие ожидаемому UID или ещё не наблюдаемые объекты делают состав неполным.
Интерфейс явно сообщает это и не выдаёт отсутствующие сведения за пустой заказ.
Secret data, cloud-init, passwords и provider credentials в список не попадают.
Список — снимок текущего развёртывания; пока заказ изменяется, состав тоже может измениться.

## Порядок удаления

После отключения защиты Dashboard посылает DELETE с UID и resourceVersion.
Admission проверяет запрос ещё раз. Для Composition-заказов Usage и finalizers
обеспечивают порядок очистки: например, балансировщик удаляется до его целей,
а служебные credentials сохраняются до завершения удаления потребителей.

Finalizer отвечает за завершение уже принятого удаления; это другой механизм,
не замена флагу защиты. Защита управляемых дочерних ресурсов также действует
отдельно: такие зависимости изменяют через родительский заказ, см.
[управляемые ресурсы](../operator-manual/managed-resources.md).
