# Частые вопросы

## Почему после создания пользователя нет проектов?

Учётная запись разрешает войти. Проект открывает отдельное назначение роли
в его namespace. Создайте RoleBinding на auditor или другой подходящий уровень.

## Нужно ли создавать группу для каждого пользователя?

Нет. Роль можно назначить напрямую User. Группа нужна, когда нескольким
пользователям требуется общий набор назначений.

## Чем Project отличается от namespace?

Namespace хранит ресурсы Kubernetes, а Project делает его проектом консоли
с пользовательским названием и описанием. Удаление только Project не удаляет
namespace и нагрузки.

## Почему viewer и editor дают одинаковый результат?

Пока реальные API продуктов не подключены к каталогу ролей, оба уровня
совпадают с auditor. Демонстрационный продукт в меню не добавляет права сам.

## Может ли owner назначить cluster-admin?

Роль owner по умолчанию не даёт такого права. Bind ограничен каталогом,
а native Kubernetes проверяет попытки эскалации. Дополнительные явно выданные
права пользователя учитываются независимо.

## Можно ли уже создавать VM и базы из форм?

Да, если оператор подключил ProductResource с целевым GVK и контрактом
операции, а страницу настроил как Create/Edit. Сервер проверяет JSON Schema,
выбранные ссылки и Kubernetes RBAC, затем записывает CR. Установленный provider
или оператор выполняет provisioning. Обычная форма без resourceRef продолжает
только проверять ввод. [Пример IaaS](operator-manual/iaas.md).

## Достаточно ли Product для полноценного IaaS или PaaS?

В текущей версии Product описывает каталог и меню, а ProductPage — форму
или представление ресурсов. Для страницы ресурсов можно указать API version,
kind и поля отображения. ProductResource связывает тип CR с CRUD, lookup и
действиями; его формы используют canonical schema серверной операции.
Управление инфраструктурой выполняет установленный контроллер: например,
Crossplane provider вместе с Composition либо оператор конкретного сервиса.
Наличие пункта PostgreSQL в каталоге само по себе не устанавливает СУБД,
её резервное копирование, восстановление или отказоустойчивость.

При подключении существующих ресурсов сначала проверьте их API и namespace,
права пользователя и фактическую поддержку операций контроллером. Настройка
просмотра описана в [страницах ресурсов](operator-manual/resource-pages.md).

## Где отчёт по расходам проекта?

В дополнительном Gator Cost. Сейчас его интерфейс административный,
открывается через port-forward и не связан с сессией Dashboard.
Попросите администратора биллинга предоставить отчёт нужного проекта.

## Почему расход Estimated?

Наблюдение источника прерывалось. Система продолжила последнее известное
состояние как оценку и показывает её возраст. Это не точное восстановление
изменений, которые произошли за время пропуска.

## Можно ли увеличить число реплик Dashboard?

Сессии находятся в памяти каждой реплики. Текущая установка использует одну.
Несколько реплик требуют отдельного решения хранения или маршрутизации сессий.
Увеличение replicas само по себе не делает вход устойчивым.

## Нужно ли сохранять данные Dashboard?

Нужны конфигурация, каталог, проекты, RBAC и внешние credentials. Сессии
сохранять не нужно. Dex и биллинг имеют собственные базы/PVC, для них нужен
отдельный план [резервного копирования](operator-manual/backup.md).

## Почему обновился Pod, а CRD остался прежним?

Helm устанавливает CRD при первой установке, но не обновляет существующие
схемы автоматически. Примените совместимые CRD из новой поставки отдельно
по инструкции [обновления](operator-manual/upgrading.md).
