---
title: Логи заказанного ресурса
---

В карточке S3-бакета доступны вкладки **Access logs** и **Error logs**.
Access показывает запросы к этому бакету, Error — запросы с HTTP 4xx/5xx.
Логи хранятся 30 дней; доступны только записи, сделанные после создания текущего
заказа. Удаление заказа закрывает доступ к его логам. Новый бакет с тем же именем
не получает историю прежнего экземпляра.

Выберите сутки, 7 или 30 дней и нажмите **Обновить**. Поле поиска принимает слово,
request ID либо выражение LogsQL, например `http_status:=404`. Фильтр бакета
проверяется сервером и сохраняется при любом поиске. Для автоматического обновления
включите переключатель: каждые 5 секунд выполняется новый авторизованный запрос.
Отображаются до 200 записей; скачивание сохраняет именно текущий результат в NDJSON.
Уточните период и поиск, если записей больше.

Таблица содержит время, операцию, объект, HTTP-статус, S3 error code, request ID,
длительность и объём переданных данных. Общие daemon/debug ошибки RGW/Ceph,
учётные данные и внутренние адреса в этот источник не входят. 403 отражает
отказ в S3-запросе, а не право пользователя Dashboard читать чужой бакет.

Нужны доступ к проекту, чтение самого Bucket CR и отдельное разрешение чтения
проектного LogAccess. Штатные S3-роли включают его. Доступ к S3 по ключу приложения
сам по себе не открывает Dashboard и его логи. Запрос к чужому проекту/бакету,
устаревший UID или отозванные права не возвращают записи.

Если записей нет, проверьте выбранный период и выполните запрос к бакету внешним
S3-клиентом. Записи поступают асинхронно. При сообщении о неготовой identity
дождитесь готовности Bucket. При отказе в доступе обратитесь к администратору проекта.

## Мониторинг → Логи

Общий экран логирования находится в разделе **Мониторинг → Логи**.
Выберите источник и все доступные заказы либо конкретный ресурс, затем период:
5/30 минут, час, 6 часов, сутки, 7/30 дней или собственные даты. Список содержит
только источники с действующим LogAccess и заказами, доступными по Kubernetes RBAC.
Общий просмотр требует list и get основного GVK; выбор конкретного заказа проверяет
его текущий UID. Логи других проектов и незакреплённых за заказом объектов не входят
в область запроса даже при знании их имён.

Введите LogsQL и нажмите **Выполнить запрос** либо Ctrl/⌘+Enter. Можно добавить до
четырёх независимых запросов A–D. Каждый выполняется в одной и той же выбранной
области доступа. Например:

```text
*
http_status:=404
* | stats count() as count
* | stats count() as count by (operation)
```

Последние два примера используют разрешённую вычисляемую колонку `count` S3
источника. Для других продуктов разрешённые поля результата задаёт их чарт.
Синтаксис и имена полей — VictoriaLogs LogsQL; редактор не переводит язык Яндекса.

Гистограмма показывает количество **всех подходящих исходных записей** в периоде,
независимо от лимита строк таблицы. Агрегирующие pipes не меняют смысл этой
гистограммы. A–D отмечаются отдельными цветами. Таблица показывает до выбранного
лимита 100/200/500/1000 строк на запрос, включая разрешённые вычисляемые колонки.
Вкладка JSON, раскрытие записи, выбор колонок и NDJSON работают с этим же
результатом. В раскрытой записи поле можно добавить в первый запрос.

Автообновление повторяет последний выполненный запрос. Черновик редактора не
отправляется автоматически. Смена проекта/источника/ресурса отменяет запросы и
очищает результаты. Кнопка «Источники» обновляет каталог заказов; после удаления
или пересоздания ресурса выберите его заново. Пустая область не открывает весь
VictoriaLogs tenant. При некорректном LogsQL исправьте синтаксис и повторите запуск.
