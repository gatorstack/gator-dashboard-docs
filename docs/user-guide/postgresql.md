# Managed PostgreSQL

Откройте **Все сервисы → DBaaS → Managed PostgreSQL** в выбранном проекте.
Сервис создаёт выделенные хосты PostgreSQL и управляет ими через Kubernetes API.

## Создать кластер

1. Откройте **Кластеры → Создать кластер PostgreSQL**. Сверху выберите
   **Single-node** либо **Patroni cluster**. Single-node содержит один хост,
   Patroni — три хоста в разных зонах одного региона.
2. Укажите имя, метки и версию PostgreSQL.
3. Выберите регион и готовую сеть VPC выбранного проекта.
4. Выберите **Флейвор** из списка выбранного региона. В его характеристиках
   указаны vCPU и RAM. Затем задайте тип и размер диска каждого хоста;
   стоимость Patroni учитывает три комплекта ресурсов. При смене региона
   флейвор нужно выбрать заново.
5. В разделе **Хосты** отдельно выберите зону и подсеть каждой строки.
   Список подсетей учитывает регион, сеть и зону этой строки. Готовые размещения
   для заказа выбирать не требуется. На телефоне строки отображаются блоками.
6. Для каждого хоста настройте **Публичный доступ** и **Приоритет primary**.
   Без публичного доступа подключение к PostgreSQL хоста идёт по приватному
   адресу из связанной сети. При включении доступен внешний адрес, с ограничением
   клиентскими CIDR. Служебные SSH/метрики не открывают публичный PostgreSQL.
7. Укажите IPv4 CIDR приложений или VPN и лимит подключений, проверьте оценку
   стоимости, оставьте защиту от удаления включённой и создайте кластер.

Приоритет 0 означает обычного кандидата; большее значение повышает предпочтение
при автоматическом failover. Он не переключает текущий primary немедленно и
не отменяет проверки актуальности WAL и доступности кандидата. У Single-node
автоматического failover на другой хост нет.

При переключении Patroni на Single-node заполненные лишние строки сохраняются
до явного удаления. Ошибка формы или источника подсетей не стирает остальные
настройки. Изменение зоны очищает только подсеть соответствующего хоста.

Если сетей или подсетей нет, создайте готовую сеть VPC либо обратитесь к
администратору. Для Patroni нужна одна сеть с подсетями в трёх разных зонах
одного региона. Межрегиональное размещение запрещено.

Состояние `Pending` или `Configuring` означает подготовку инфраструктуры и
PostgreSQL. `Ready` появляется после выполнения плейбука и проверки доступности
PostgreSQL на хостах и, для Patroni, TLS через primary endpoint. `Degraded`
требует проверки служебного мониторинга.
Карточка показывает условия, безопасное сообщение и наблюдаемые адреса хостов.

## Подключение

В карточке кластера откройте **Обзор → Подключение**. Для чтения требуется
отдельное Kubernetes разрешение `get` на указанный Secret; обычный просмотр
кластера не раскрывает пароль. Администратор может назначить созданную вместе
с заказом Role `postgresql-<идентификатор-заказа>` в namespace проекта.

Сохраните публичный CA сертификат из поля `ca.crt` в файл `postgresql-ca.crt`.
Для PostgreSQL клиента используйте полученные host, port, username и database:

```sh
PGSSLROOTCERT=postgresql-ca.crt psql \
  'host=POSTGRESQL_ENDPOINT port=5432 dbname=postgres user=gator_admin sslmode=verify-full target_session_attrs=read-write'
```

Замените POSTGRESQL_ENDPOINT значением host из данных подключения: у Patroni это
единый адрес балансировщика, у single-node — адрес хоста. Пароль вводится в
запросе клиента. `target_session_attrs=read-write` дополнительно проверяет, что
соединение попало на writable primary. Клиентская сеть должна иметь маршрут к адресу сервиса; наличие
разрешающего CIDR само по себе маршрут не создаёт. В лабораторной установке
Floating IP может быть доступен только через VPN.
Список клиентских сетей меняется через **Изменить** в карточке кластера.
Изменение правил доступа не перезапускает PostgreSQL.

`gator_admin` имеет права создания БД и ролей, без superuser/replication.
Служебные PostgreSQL superuser и SSH private key клиенту не выдаются.

## Базы данных и пользователи

Управление находится в отдельных разделах меню продукта. Вкладки «Базы данных»
и «Пользователи» в карточке кластера пока скрыты.

В разделе **Пользователи** создайте пользователя нужного кластера. Пароль
генерируется сервисом и выдаётся через отдельный connection Secret. Укажите
лимит подключений; `-1` означает отсутствие отдельного ограничения роли.

В разделе **Базы данных** выберите тот же кластер, имя БД и владельца:
`gator_admin` либо готового пользователя этого кластера. Сервис использует UTF8
и локаль `C.UTF-8`. Имена `postgres`, `template0`, `template1`, служебные имена и
префиксы `pg_`/`gator_` зарезервированы. Пользователь без прав на кластер не может
управлять его БД через консоль.

Удаление БД удаляет её данные. Перед удалением пользователя удалите или
переназначьте принадлежащие ему объекты PostgreSQL; ошибка зависимостей остаётся
видна в состоянии заказа. Данные PostgreSQL обслуживаются стандартными SQL
клиентами, встроенного web SQL редактора нет.

## Мониторинг, события и операции

Вкладка **Диагностика** карточки содержит блок **Состояние**: условия Ready,
Synced и Responsive с причинами и сообщениями контроллеров.

На вкладке **Мониторинг** показаны метрики выбранного кластера по хостам:
доступность PostgreSQL, подключения, транзакции и откаты в секунду, роль узла
и задержка применения WAL. Роль 0 означает primary, 1 — replica. Доступны
выбор периода и автообновление; нужны права мониторинга проекта. Данные старше
90 секунд исключаются, отсутствие метрик не подменяется нулём.

В **Мониторинге → Дашборды → Managed PostgreSQL** выберите кластер. Доступны
доступность хостов, подключения, commits и rollbacks. Серии изолированы проектом
и UID кластера. При отсутствии экспортера `Ready` не устанавливается.

Вкладка **Логи** карточки показывает серверные события: время, severity,
SQLSTATE, тип процесса, сессию и БД. SQL, параметры запросов, детали ошибок и
пароли в клиентский поток не передаются. Поиск ограничен текущим заказом и
периодом хранения платформы. **История** содержит действия Kubernetes API.

В **Операциях** задайте уникальное имя операции и выберите `restart` либо `switchover`. Переключение доступно для
трёхузлового Patroni. Завершённая операция сохраняется как запись и повторно
не выполняется после перезапуска контроллера.

## Квоты, расходы и удаление

Главная проекта показывает квоты Managed PostgreSQL: кластеры, хосты, vCPU,
RAM и объём дисков. Ресурсы считаются с множителем числа хостов. Admission
проверяет те же лимиты при обращении напрямую к Kubernetes API.

Цена заказа берётся из тарифов Cost/OpenMeter. Начисления продолжаются при
временной недоступности PostgreSQL, пока выделенные ресурсы существуют.
ВМ кластера видны в IaaS как «Управляется заказом» со ссылкой на PostgreSQL.
Они не создают второе начисление Compute. Учебные цены не являются
коммерческим предложением.

Для Patroni автоматически создаются балансировщик и целевая группа в разделе
сетевой инфраструктуры. Оба помечены «Управляется заказом»; меняйте параметры
через кластер PostgreSQL. Прямое редактирование, удаление и удалённые действия
для его ВМ недоступны, чтение определяется вашими ролями соответствующих продуктов.

В обзоре кластера показан единый адрес primary на порту 5432. Балансировщик
проверяет HTTPS Patroni `/primary` на порту 8008 и направляет новые подключения только
на текущий основной узел. После переключения роли подключайтесь по прежнему адресу;
приложение должно повторять разорванные подключения и незавершённые транзакции.
При отсутствии primary новые подключения не переходят на read-only реплики.
Клиентские сети кластера ограничивают доступ и к этому адресу. TLS проходит до
PostgreSQL; используйте `sslmode=verify-full` и CA из данных подключения.

Для удаления сначала удалите зависимые БД, пользователей и записи операций,
затем выключите защиту от удаления и удалите кластер. Контроллер дожидается
удаления собственных VM и сетевых ресурсов. Сначала удаляется кластер, затем
использовавшаяся им сеть VPC.

В этой версии параметры размещения, версии, размеров и класса фиксируются при
создании. Single-node не обеспечивает высокую доступность. Автоматическое
резервное копирование, PITR, изменение топологии и major upgrade пока не входят
в сервис; используйте стандартные клиентские средства для нужных копий данных.


Заказ представлен одним namespaced `PostgreSQLCluster` Crossplane XR. Его
инфраструктуру согласует Composition; форма заказа, роли, квоты и тарифы
применяются к этому же GVK. Служебные зависимости и credentials закрыты от
продуктовых ролей. При административном переносе существующего кластера на
Composition его UID, VM, диски и connection Secret сохраняются.
