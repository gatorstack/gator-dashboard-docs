# Managed MongoDB

Сервис создаёт MongoDB Community на выделенных виртуальных машинах OpenStack.
Откройте **Все сервисы → DBaaS → Managed MongoDB → Кластеры** и нажмите
**Создать**. Доступные конфигурации формируются из готовых подсетей проекта.

| Режим | Состав |
| --- | --- |
| single | Один standalone mongod |
| cluster | Replica set rs0: три mongod, по одному в каждой зоне |
| shard | 2–4 shard replica sets по три mongod, три config servers и два mongos |

Минимальный shard содержит 11 VM. Каждый replica set размещается в трёх зонах
одного региона и сети. Это логическое распределение; физическая отказоустойчивость
зависит от инфраструктуры площадки.

Выберите расположение, класс ресурсов каждого хоста, диск, начальную БД и
клиентские IPv4 сети. CIDR открывают MongoDB TCP/27017; у клиента должны быть
маршруты до адресов сервиса. Включённая по умолчанию защита предотвращает удаление.
Размер диска и класс применяются ко всем VM, включая config servers и mongos.

Карточка показывает состояние и вкладки **Хосты**, **Подключение**, **История**.
`Ready` означает успешную проверку TLS и аутентификации, здоровья replica sets
и состава shards. При `Pending` смотрите сообщение; пока ресурс не готов,
подключение может отсутствовать.

Во вкладке подключения доступны MongoDB URI, CA сертификат, имя БД и учётная
запись `app`. Для получения этих значений нужны права чтения конкретного Secret;
роли сервиса сами по себе их не предоставляют. Получите CA отдельным файлом и
передайте его клиенту как `tlsCAFile`. Проверка сертификата обязательна.
Не сохраняйте URI с паролем в shell history или общем журнале.

Учётная запись `app` имеет `readWrite` только в начальной базе; в shard она
также может включать шардирование её коллекций, без доступа к другим БД. Коллекции и
индексы создаются обычным MongoDB клиентом. В режиме shard подключайтесь к
mongos из выданного URI. Включение шардирования конкретной коллекции и выбор
shard key доступны учётной записи app в начальной БД через MongoDB клиент; наличие
sharded topology не распределяет автоматически каждую коллекцию.

Имена replica members должны разрешаться в DNS на стороне клиента. Оператор
выбирает домен; в учебной установке это sslip.io с адресами floating IP.

После создания можно менять клиентские CIDR, метки и защиту от удаления.
Топология, число shards, версия, расположение, начальная БД, класс и диски
неизменяемы. Перед удалением отключите защиту. Удаление уничтожает VM и диски.
Резервное копирование/PITR, resize, upgrade, биллинг, доставка серверных логов
и продуктовые графики в первой версии не подключены.

Для шардирования коллекции подключитесь к mongos с CA и вводом пароля по запросу
(имена хостов возьмите из Secret):

```sh
mongosh 'mongodb://mongos-1.example.org:27017,mongos-2.example.org:27017/app?authSource=app&tls=true' \
  --username app --tlsCAFile ./ca.crt --password
```

В интерактивном клиенте создайте коллекцию с hashed shard key:

```javascript
db.getSiblingDB('admin').runCommand({
  shardCollection: 'app.events',
  key: { _id: 'hashed' }
})
```

Ожидается `ok: 1`. Выбор shard key зависит от запросов вашего приложения;
пример не заменяет проектирование распределения данных.
