# Квоты проекта

## План и факт

В Dashboard выберите проект и откройте **Home → Квоты**. Группы задаются администратором. Строка — один показатель (`metric`)
объекта Quota; внутри могут быть общий и региональные лимиты. Столбец **Использование** показывает текущее
значение и установленный лимит. **Зарезервировано** — запросы, которые webhook
уже проверил, но запись которых ещё не подтверждена. **Доступно** учитывает оба.
Страница показывает только список показателей и использование, без переходов
в отдельные квоты. Правила и подробное состояние доступны через Kubernetes API.

Через CLI с вашим контекстом:

```sh
oc --context YOUR_CONTEXT -n project-a get quotas.quotas.gatorstack.dev
oc --context YOUR_CONTEXT -n project-a get quota compute -o yaml
```

Пример `status` при лимите 100 CPU:

```yaml
status:
  hard: {cpu: '100'}
  used: {cpu: '14'}
  reserved: {cpu: '4'}
  available: {cpu: '82'}
  overage: {cpu: '0'}
```

`used` — факт, рассчитанный по полям записанных объектов. `hard` — план/лимит.
Для `sum(.spec.cpu.count)` машины с 2, 4 и 8 CPU дают 14. Для `count(.)`
те же объекты дают 3. Правила и несколько квот проверяются одновременно.
Они не отменяют друг друга и не складывают лимиты.

### Количество ConfigMap и ключей

Для `v1/ConfigMap` правило `count(.)` считает ConfigMap в namespace, а
`sum(count(.data) + count(.binaryData))` — суммарное количество ключей в их
data и binaryData. Например, два ConfigMap с 2 и 3 ключами дают факт 2 по
объектам и 5 по ключам. Одинаковый ключ в разных ConfigMap считается отдельно.
Пустое значение тоже занимает один ключ; изменение значения квоту не расходует.
Пустой ConfigMap занимает один объект и ноль ключей. Metadata не участвует.

В расчёт входит стандартный ConfigMap `kube-root-ca.crt` с ключом `ca.crt`.
Поэтому в новом namespace факт обычно начинается с 1 объекта и 1 ключа.
При увеличении data/binaryData проверяется общий остаток namespace. Удаление
ключей освобождает ёмкость после записи; удаление ConfigMap освобождает оба лимита.

## Группы, регионы и фильтры

Страница показывает группы **С потреблением** и **Без потребления**. В каждой
группе есть иконка, все группы при открытии страницы свёрнуты. Нажмите на
заголовок, чтобы открыть показатели. Выбранное раскрытие сохраняется при поиске,
фильтрации и обновлении данных, пока страница открыта. Под названием указан
технический ID одной строкой: имя Quota + точка + metric (например, compute.vcpu).
Название показателя отображается обычным текстом.
Поиск работает по названию, ID, имени Quota и группе. Заголовки столбцов
позволяют сортировать по названию или доле занятого лимита.

Фильтр **Регионы и зоны** оставляет выбранную область и общий показатель.
Лимиты без региональной разбивки остаются видимыми. «Всего» вычисляется своим
правилом: это не сумма региональных строк, области могут пересекаться.
Переключатель **Почти закончились** показывает показатели, где использование
вместе с резервами достигло 80% хотя бы одного видимого лимита. Порог задаётся
схемой страницы. Жёлтый индикатор означает приближение к пределу, красный —
достижение или превышение. Зарезервированная ёмкость подписана отдельно.

Если расчёт неактуален, экран показывает предупреждение и последнее известное
значение без индикатора. Отсутствующий факт отображается как «—», а не ноль.
Проверьте Quota.status через Kubernetes API или обратитесь к администратору. Запроса
увеличения и истории запросов в интерфейсе нет; лимиты меняет администратор.

## Создание и изменение ресурсов

Пользуйтесь обычной формой Dashboard или Kubernetes API. Отдельный запрос
резервирования не требуется. При UPDATE проверяется увеличение вклада,
например 4→8 CPU требует ещё 4 CPU. Если объект исключён selector, он не
участвует; переход под selector проверяется как увеличение. Уменьшение spec
освобождает декларированную ёмкость после записи, удаление — после исчезновения
CR. Объект с deletionTimestamp продолжает учитываться.

Предварительная проверка без расходования квоты:

```sh
oc --context YOUR_CONTEXT -n project-a create --dry-run=server -f resource.yaml
```

dry-run — проверка текущего состояния, он не закрепляет остаток за вами.
Окончательный CREATE/UPDATE может получить отказ, если ёмкость занял другой запрос.

## Отказ или ошибка расчёта

Webhook возвращает настроенное сообщение и ограничивающее правило, лимит,
факт, резерв и запрошенное увеличение. Уменьшите запрос, освободите ненужные
ресурсы или попросите администратора увеличить `spec.rules[].hard`.

Если `Ready=False`, посмотрите сообщение условия. Неверное/отсутствующее
числовое поле и недоступный API не считаются нулём. Последний факт может быть
устаревшим; время последнего успешного расчёта — status.lastCalculatedTime. Ошибки расчёта
могут блокировать UPDATE, включая уменьшение, пока источник не исправлен;
удаление доступно независимо от webhook.

Если резерв долго не исчезает, передайте администратору namespace, имя квоты
и имя операции/ресурса. Не удаляйте служебный журнал. Квоты и лимиты меняет
администратор; проектные роли имеют только get/list/watch Quota.

Квота не считает деньги и не проверяет, освободил ли cloud provider физические
ресурсы. Формула определяет, какие поля CR считаются фактом.
